- **`max_concurrent > 1` now has real concurrency tests.** The setting was covered only by parsing assertions (`_max_concurrent_jobs()` defaults to 1, the API round-trips the field) and by nothing that ran two jobs at once — the last open finding from the 2026-07-25 adverse-conditions audit, and the behaviour the README's pueue/task-spooler migration table points migrants at for "parallelism limits". `tests/test_worker_concurrency.py` pins the ordering that actually bounds concurrency (`_reserve_and_dispatch` records the reservation synchronously in the poll thread, before it returns), that N jobs genuinely overlap at a cap of N, that the gate stops at the cap, that the heartbeat's `running`/`in_flight_job_ids` track live reservations, and that `_allocations_total` sums every pending claim rather than the newest. A guard also pins the real poll-loop gate expression, since the tests mirror it rather than driving the HTTP loop. Note for future test authors: the first version of these tests passed even with the historical bug reinstated — asserting on a count after `Thread.start()` is a race that usually resolves in the buggy code's favour — so the ordering tests now prevent the worker thread from running at all, which makes the two implementations distinguishable with certainty.
