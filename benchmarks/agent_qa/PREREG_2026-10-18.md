## Why, and what changed

`diagnose.py` on the 10-16 transcripts (123 runs per arm, prices fitted to
every run's cost): both arms cost $4.66 and $4.65 in total. Tool definitions
were not the cause. The first call's context was 6,300 tokens with the server
against 2,500 with Bash, but most of it was read from cache ($0.20/M), and the
median server run took 2 turns against 3. One kind of question was: the 18
"failed jobs of a project on a day" runs cost the server $2.12, 45% of its
total. Their median was 6.5 turns and 11,000 characters of tool output,
because `jobd_list` has no date filter and its rows have no `finished_at`.
No call was refused for a bare tool name, and no parallel call failed (21
API messages carried more than one call).

The changes (MCP side only; the broker's `GET /jobs` already returns
`finished_at` and pages with `limit`/`offset`):

- `jobd_list(finished_after=, finished_before=)`: ISO-8601 or relative
  (`3d`). The server pages through the filtered set and filters by
  `finished_at` itself; `counts` then cover the window exactly.
- `finished_at` and `duration_s` on every `jobd_list` row.
- A note at the top of the instructions that the client lists each tool
  under its prefix (`mcp__jobd__jobd_list`).

The 10-16 questions put both arms at 41 of 41, so they cannot show an
accuracy difference. The confirmatory sweep uses a new, harder set.

## Primary endpoint and win rule

Primary endpoint: questions right in all 3 runs, mcp against alt, out of 38.
A run that is invalid (the 10-16 validity rule: exit, tools, no tool call,
leak scan) does not count as right.

- **Non-inferior:** mcp >= alt − 2.
- **Better:** an exact two-sided McNemar test on the discordant questions
  gives p < 0.05 with more questions that only mcp got right, and the
  bootstrap 95% CI (10,000 resamples of questions, seed 20261016) of
  (mcp − alt) / 38 lies wholly above 0.
- **WIN** = non-inferior and better. **LOSS** = not non-inferior, or alt
  significantly better (p < 0.05, CI wholly below 0). Anything else is a
  **TIE**. Implemented as `analyze.win_rule` and tested in
  `tests/test_agent_qa_rerun.py`.

Secondary (reported, not deciding): right per run, cost and seconds per answer
(bootstrap ratios, sign tests), the baselines, accuracy by kind, and the
mechanism readout: how many mcp runs passed `finished_after` or
`finished_before`, and calls refused for a bare name. If no run used the
window, the window was not tested.

Expectation, written down so it can be wrong: the window kinds (27 of 38
questions) favour the server, because the CLI's `job list` prints no times
and the CLI arm must run `job status` per job or rebuild a window from
`job audit`. The event and log kinds should be even. The server arm has no
arithmetic tool, so summed run times may go against it. A tie is likely if
the CLI arm also gets the window questions right with jq.

## Usage limits and harness failures

Start only if the newest transcript's five-hour utilization is below 0.50.
`run.py` pauses until `resetsAt` whenever a transcript shows five-hour
utilization >= 0.85 or a `rejected` status, records every pause in
`pauses.jsonl`, and stops if seven-day utilization is >= 0.80. A row the API
ended before the model answered (`run.api_failure`: a rate-limit rejection
with no successful result, or a result with terminal reason `api_error`;
decided from the transcript alone) is a harness failure. After the sweep,
`run.py --drop-api-failures` sets these aside, and the sweep is resumed to
re-run each once. A row the API ends again stays in and counts as invalid.
Timeouts are not re-run.

## Analysis

```bash
R=~/jobd-artifacts/agent_qa/rerun-2026-10-18
uv run python benchmarks/agent_qa/analyze.py --key $R/questions.json --runs $R/runs \
  --results $R/results.jsonl --outdir benchmarks/agent_qa/rerun_2026-10-18
uv run python benchmarks/agent_qa/diagnose.py $R/runs
```

No other retries. An interrupted sweep is resumed (`run.py` skips finished
runs), never restarted, and never stopped early on interim results.

One pilot preceded this file, to check the harness on the git spec: h02 in
both arms, 1 rep. alt was right with 12 `job` calls ($0.22, 75 s); mcp was
right with one `jobd_list` call using the window ($0.077, 13 s). The alt run
read five-hour utilization 0.96, so the gate paused the pilot; it was stopped
to free the shared sweep lock and the mcp run made after the 11:10 EDT reset
(five-hour 0.02, seven-day 0.25). The pilot is kept apart
(`rerun-2026-10-18/pilot/`) and is not part of the analysis.
